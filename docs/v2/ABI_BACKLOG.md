# Server-Host V2 ABI and reverse-engineering backlog

This is the contract queue for V2. It intentionally includes known contracts:
“known” ABI still needs an implementation card and runtime validator. A workflow
may consume a contract only when its status reaches **device-proven** for the
named build and postcondition.

Status meanings:

- **exact-binary** — semantics or layout confirmed in the exact 1.10280 iOS
  binary, but not necessarily invoked by V2;
- **sdk+source** — current FreshSDK and/or current local source agree; binary or
  runtime validation is still missing;
- **control-proven** — behavior passed in the 0.2.11 control, without recovered
  source or a V2 artifact;
- **partial** — some address/layout/call facts are known, but an essential ABI,
  lifecycle, ownership or postcondition is missing;
- **unknown** — no sufficient current contract;
- **deferred** — explicitly outside near-term iOS gates;
- **device-proven** — captured V2 behavior for an exact artifact and bounded
  postcondition; it does not imply unreported soak coverage.

Priorities are `P0` (blocks the next gate), `P1` (blocks stable gameplay), `P2`
(later iOS workflow) and `P3` (deferred platform/product).

## 2. Required function/layout card format

Every ABI-bearing implementation adds one reviewable card containing:

```text
contract ID and workflow
exact build identity and platform
symbolic name plus confidence (known name / inference / unknown)
resolution method and expected unique hit count
RVA only as diagnostic metadata
function type or sizeof/align/offset/mask
instruction, vtable, class and reflection validators
ownership and nullability
thread and reentrancy requirements
preconditions, original-call and rollback rules
observable postcondition
negative/unsupported-build behavior
IDA locations, SDK declarations, logs and device artifact IDs
reviewer decision and expiry/revalidation trigger
```

An RVA with a plausible pseudocode body is not a complete function card.

## 4. Deliberate RE boundary

Gate 0 does not reverse every administration, save or SEA protocol operation.
The exact iOS database remains the source for near-term host/player contracts.
`SEAServerManager.dylib.i64` is opened when its control-plane workflow becomes
active; the Android database is requested only after its exact path is supplied.
This boundary prevents future speculative APIs from entering the typed core.
